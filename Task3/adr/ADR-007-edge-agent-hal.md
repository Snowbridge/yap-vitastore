# ADR-007. Web POS + Edge Agent (HAL) на планшете, облачный Payment Gateway, политика оборудования

**Статус**: ✅ принято

## Контекст

Цель бизнеса: в магазине остаются только планшет и фискальный регистратор, локальных серверов нет. Касса — тонкий клиент (Web POS или лёгкое приложение на планшете) ([ADR-006](ADR-006-own-cloud-pos.md)).

Ограничения постановки Task3:

- в купленных магазинах разные ФР и банковские терминалы (Сбер, Альфа, Ingenico, Verifone);
- кассовое приложение из облака не может напрямую работать с USB- и COM-портами устройств.

В Task1 (5.3) уже решено: стандартный комплект — планшет + ККТ АТОЛ / Штрих-М + PIN-pad, планшеты управляются через MDM.

## Разрыв в постановке

1. **G21.** Нужен тонкий клиент, но браузер не имеет доступа к драйверам ККТ и терминалов. WebUSB / Web Serial нестабильны на Android, их нет в iOS, и они не дают вендорских SDK.
2. **G22.** Task1 вводит стандартный комплект, а Task3 требует работать с разнородным парком купленных сетей. Неясно, что унифицируется, а что поддерживается как есть.

## Решение

1. **Web POS (PWA)** — весь UI и сценарии кассы.
   - Статика раздаётся из Yandex Object Storage + Cloud CDN, обновление — без участия магазина.
   - Бизнес-логика (цены, промо, лояльность, остатки) выполняется в облаке. Для офлайна в Edge Agent есть урезанный движок расчёта чека по кэшу ([ADR-008](ADR-008-offline-mode.md)).
2. **Edge Agent** — лёгкое Android-приложение (foreground service) на том же планшете. Устанавливается и обновляется через MDM. Состоит из трёх модулей:
   - **HAL** — единые интерфейсы `IFiscalPrinter` (открыть смену, напечатать чек, X/Z-отчёт, статус ФН) и `IPaymentTerminal` (оплата, возврат, отмена, сверка итогов). Реализации — плагины по вендорам и протоколам: АТОЛ, Штрих-М; Сбер (ARCUS-2), Альфа-Банк, Ingenico, Verifone. Транспорт плагина — USB, Bluetooth или TCP/IP. Плагин загружается по профилю устройства из Device Registry.
   - **Offline Store + Sync** — локальный кэш и outbox ([ADR-008](ADR-008-offline-mode.md)).
   - **Local API** — WebSocket/REST на `127.0.0.1`. Web POS вызывает `fiscal.printReceipt`, `payment.pay` и не знает модели устройства. Доступ — по токену, который выдаётся при регистрации планшета в Device Registry.
3. **Payment Gateway** — собственный облачный сервис (PaaS):
   - единый Payment API для Web POS: создание платежа, статус, возврат, СБП по QR;
   - маршрутизация к эквайреру по профилю магазина и терминала;
   - хранение профилей терминалов, ежедневная сверка с реестрами банков, сводная отчётность;
   - физическую авторизацию карты выполняет терминал через канал банка, PAN и PIN в Payment Gateway и Edge Agent не попадают. HAL получает от терминала только результат: код авторизации, RRN, маскированный номер.
4. **Политика оборудования при онбординге:**
   - **ФР меняются на стандарт АТОЛ / Штрих-М.** При смене владельца ККТ всё равно снимается с учёта и регистрируется на ИНН VitaStore с новым ФН, поэтому замена устройства почти не добавляет работ. HAL держит два фискальных плагина.
   - **Банковские терминалы остаются.** Чаще всего они принадлежат банку-эквайреру по договору купленной сети. Их подключают HAL-плагин и профиль в Payment Gateway. Переход на единого эквайрера — коммерческое решение по истечении договоров, архитектура от него не зависит.

## Последствия

- Новый банк или модель терминала — это новый плагин Edge Agent, который выкатывается через MDM, и профиль в Payment Gateway. Web POS и backend не пересобираются (INC-8415: 3 недели → 2-5 дней на плагин, а для известной модели — только настройка).
- Edge Agent — единственный нативный компонент. Его версия контролируется MDM, совместимость с Web POS — версионированием Local API.
- В магазине нет сервера: планшет, ККТ, PIN-pad и роутер с LTE-резервом. Выход планшета из строя закрывается подменным фондом и повторной регистрацией за минуты (INC-8433).
- PCI DSS: карточные данные не проходят через Web POS, Edge Agent и Payment Gateway, поэтому область аудита минимальна.
